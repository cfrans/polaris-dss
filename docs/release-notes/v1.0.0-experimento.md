# Polaris DSS v1.0.0-experimento

Frozen code for the data collection of the undergraduate thesis experiment (manual baseline versus
human-in-the-loop remediation). Data reported in the thesis must cite this tag and its commit.
Any code, configuration or schema change during collection invalidates the sample: discard the
affected rounds, publish `v1.0.1-experimento` and restart.

## What the system does

Polaris receives Zabbix problems by webhook and reconciliation, keeps global event identity and
matches three rules (R001 disk, R002 CPU, R003 nginx) with an explained confidence index. Before
approval, a fixed read-only collector inspects the target and the card offers specific actions:
remove a root-owned `.log.gz` retained for seven days or compress a closed `.log` (R001); terminate
the highest allowed CPU consumer using at least 50% of one CPU in a three-second sample (R002);
start or restart nginx when its observed state allows it (R003). Approval is persisted in
`audit_log` before any execution; the central executor (`apply_action.py`) revalidates the exact
approved target over SSH and never chooses another one. Destructive or low-confidence actions
require an explicit confirmation step.

## Experiment instruments

Explicit administrative injection for the three scenarios, an independent recovery observer
shared by both arms (t5 is the first healthy sample of the confirmed window; CPU requires 30 s
below 70%), incident linking, human assessment, discard with reason, backup, descriptive report
and explicit reset with two global health samples 30 s apart. The manual arm follows the
operator knowledge base in `experiment/kb_operador/` (R001 and R002 from the KB, R003 from memory).

## Validation before freezing

- Full test suite on Linux with disposable PostgreSQL 16.15: 570 passed, 2 optional graph tests
  skipped; 40 JavaScript tests passed.
- Six laboratory rehearsals on 2026-10-17, one per scenario and arm, all discarded as rehearsal:
  R003, R001 and CPU in the HITL arm and in the manual arm. Defects found in them were fixed
  before this tag (CPU option threshold, CPU recovery timestamp, confirmation clarity, removal of
  the generic cleanup and process scripts).
- Changelog items marked **[NÃO VERIFICADO]** were written before those rehearsals and keep the
  mark where the specific behavior was not observed in the laboratory.

## Known limitations

Single SSH target and three rules; heuristic confidence index, not a probability of success; no
authentication or roles in the interface and a self-declared operator; the service credential can
run root commands through the `timeout` wrapper, so approval guards belong to the application and
do not restrict root or direct database writes; the operator of both arms is the author, who knows
each scenario (conservative bias against the hypothesis). No comparison results exist in this
release.
